# Changelog

Semver. In `0.x` releases **a minor bump is considered breaking**. When upgrading:

```bash
dotnet add package VitalWatch.AspNetCore
dotnet run -- --vitalwatch-status
```

---

## 0.1.1

### Changed

- Docs: README, CHANGELOG and package description are now in English.
- All user-visible output (CLI, log warnings, IDE docs) is now in English: the
  `--vitalwatch-status` report, the startup warning in the `VitalWatch` log category, the
  configuration problem messages and the XML documentation (IntelliSense) of the public API.
  The release source written in code is now reported as `code`.
- The test event sent by `--vitalwatch-status --test` now has the message
  "Test event generated by vitalwatch-status --test". It gets a new fingerprint once in the
  hub, so after upgrading the next `--test` run opens a new issue instead of joining the old
  one. Generated `http_5xx` / `slow_request` messages (`GET /fail — HTTP 503`,
  `GET /slow — 1200 ms`) were already language-neutral and are unchanged, so their
  fingerprints are not affected.
- No change to behavior, exit codes or the wire format.

## 0.1.0

Initial release. Same wire contract, same masking and same environment variables as the
sibling packages (`vitalwatch-node`, `vitalwatch` for Python,
`cestnytr/vitalwatch-laravel`).

### Added

- `builder.Services.AddVitalWatch()` + `app.UseVitalWatch()` — two-line setup.
  Configuration from the `VitalWatch` section and `VITALWATCH_*` environment variables;
  the process environment overrides appsettings, and settings passed in code override both.
- Events: `exception` (with the route pattern: `GET /api/products/{id}`), `http_5xx`,
  `slow_request` (with query count and slowest query), `slow_query`, `job_failed`
  (crashed `BackgroundService`), `fatal` (out of memory).
- SQL measurement without package dependencies: EF Core and SqlClient `DiagnosticListener`,
  Npgsql `ActivitySource`. Per-request counter via `AsyncLocal`; EF plus the driver do not
  count the same command twice.
- Can be added before or after `UseExceptionHandler`; exceptions the handler turns into a
  4xx are not reported.
- Bounded queue + a single background sender; at most 8 events and 8 KB per request
  (for an event that does not fit, the stack trace is trimmed first, then the message).
- Liveness request every 8 hours (`{"events":[]}`), plus one immediately at startup.
- Automatic release tag: `VITALWATCH_RELEASE` → CI variables → `.git`
  (content root and up to three parent directories).
- Diagnostics: `dotnet run -- --vitalwatch-status [--test] [--vitalwatch]`
  (`app.RunVitalWatchStatusAsync(args)`), and a single startup warning when the
  configuration is incomplete.
- Manual reporting: `IVitalWatch` (injected) and `VitalWatchSdk.Report(ex)` (static).
- Masking is identical to the sibling packages and tested with shared vectors
  (`Fixtures/mask-vectors.json`). In the long-string mask, **plain CamelCase names are not
  treated as tokens**: a candidate with no digits or `-`/`_` that fully matches
  `^[A-Za-z][a-z]+(?:[A-Z][a-z]+)+$` is left as is — stack-trace names such as
  `InvalidOperationException` and `HandleNonSuccessAndDebuggerNotification` no longer become
  `[token]`. Strings with digits, consecutive uppercase letters, or all uppercase are still
  masked. The rule shipped to all SDKs and the hub together on 22 October 2026; in the other
  packages, messages containing such names are grouped under a new fingerprint once after
  upgrading and may trigger a single "new error" alert.
